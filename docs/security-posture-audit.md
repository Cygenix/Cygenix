# Security posture — Phase 1 findings

**Investigation only. Nothing was changed.** Every claim below was read from this
repository at the commit that added this file, and each one names where. Where the code
did not answer the question, it says so rather than guessing.

This is the audit the security-section brief asks for before any copy is written. The
brief's own rule is the reason it stops here: *"Nothing ships unverified. Where you
cannot trace a claim to code, configuration or a signed document, cut the line or
escalate it."* Several things the section would want to say are, on the evidence,
untrue today.

---

## The short version

**Three statements already on the site are wrong, not merely vague.** They are wrong in
the direction that matters — they claim less exposure than exists.

1. The homepage says the product *"runs in the browser and connects to your databases
   directly."* It does not. Every query goes through a Cygenix-operated function that
   opens the connection itself. **Customer row data transits Cygenix infrastructure on
   every run.**
2. The privacy policy says Cygenix does *"not collect the contents of the databases you
   connect to — only the schema metadata"* and that connection strings are *"never
   transmitted to our servers."* Both are contradicted by the code.
3. `UK-hosted` is imprecise. The metadata store is Azure UK South; the functions that
   handle row data are Netlify's, and Netlify processes in the US. The privacy policy
   already admits the second half; the marketing copy does not.

**Two findings are genuinely strong and are the spine of a good section**: the audit
trail records no SQL text and no values, and AI mapping sends names and types only, from
the browser, on the customer's own API key — it never touches Cygenix infrastructure.

**One finding needs a decision before anything ships**: preflight writes literal
customer values into browser storage, and the key is missing from the storage inventory
that is supposed to classify every key.

---

## 1.1 Topology — what actually opens the connection

A browser cannot open a TDS or libpq socket, and this one does not.

| Step | Where it runs | Evidence |
|---|---|---|
| Browser issues a query | The user's machine | `project-builder-app.js:1888` posts to `/.netlify/functions/db-connect` |
| The connection is opened | **A Netlify Function** | `db-connect.js` requires `mssql` and `pg` and connects with them |
| Entra-only Azure SQL | **Relayed to the Azure Function App** | `lib/azure-sql-relay.js` — Netlify has no managed identity, so the Function App runs the query |
| Scheduled and long runs | **Entirely in the Azure Function App** | `azure-function/src/run-migration.js` — replaces the Netlify runner because Netlify caps background functions at 15 minutes |

So there are **two** Cygenix-operated processes that see customer rows, not zero. There
is **no customer-hosted component** anywhere in the repository.

**Rows in flight are in the memory of a Netlify Function (AWS Lambda) or an Azure
Function.** `db-connect.js` returns result sets to the browser and takes batches back;
nothing writes rows to disk on that path that I could find. Isolation is per-invocation
process isolation from the platform, not anything Cygenix implements — that is a normal
posture, but it should be described as what it is.

**Not answered by the code, and a buyer will ask:** what a customer must open in their
firewall. Netlify Function egress and Azure Function egress are both dynamic address
ranges unless a static outbound IP is configured, and I found no such configuration and
no documentation of one. **Escalate.**

## 1.2 Sampling — where a literal customer value can come to rest

Six surfaces, as the brief expects. The answers are not uniform.

### 1. Preflight — **retains literal values, in browser storage**

`cygenix-preflight.js:220-241` keeps up to **three example values per failure code per
column**, each truncated to 60 characters:

```js
if (f.examples.length < 3) {
  const s = v === null || v === undefined ? 'NULL' : String(v);
  f.examples.push(s.length > 60 ? s.slice(0, 57) + '…' : s);
}
```

`pfSave` (line 572) writes the whole report to `localStorage` under
`cygenix_preflight_results`. It is not memory-only, and it is not counts-and-types-only.

Two mitigating facts: it stays on the device — the key is **not** in `SYNC_KEYS`, so it
does not reach Cosmos — and the examples are what make the forecast actionable.

**But the key is absent from `docs/storage-inventory.md`.** That file is generated by
`scripts/storage-inventory.js` and `tests/storage-inventory.test.js` is supposed to fail
when a key is added without a classification. I regenerated it and the key still does not
appear, so the scanner is not seeing this write site. The "every key is classified"
guarantee has a hole, and the key it is missing is one that holds customer values.
**This should be fixed before the section claims anything about where values rest.**

### 2. Validation failure reports — **not found**

The brief describes users choosing *"which columns appear in the failure report"*. I
could not locate that feature, its storage, or its retention in this repository. Either
it is named something I did not find, or the homepage describes something not built.
**Escalate — do not write copy about it either way.**

### 3. AI column mapping — **names and types only, and it does not transit Cygenix**

This is the strongest finding in the audit.

- The call is made **from the browser directly to `api.anthropic.com/v1/messages`**
  (`object-mapping-app.js:1712`, and ~20 other sites), with
  `anthropic-dangerous-direct-browser-access: true`.
- It uses **the customer's own Anthropic API key**, held in their browser. Cygenix has
  no key of its own to substitute — `netlify/functions/data-proxy.js` forwards a caller's
  key and says so explicitly.
- The prompt is built from **column names and types**. The code says so at line 1726:
  `// Log the AI access — schema only, no row data`.

Consequence worth stating plainly: **no sampled value goes to the model provider, and no
prompt reaches Cygenix infrastructure at all.** The relationship for that call is between
the customer and Anthropic, under the customer's own terms.

**This means the homepage is wrong in the other direction too.** It says mapping is
*"scored on name, type, sampled values and referential shape"*. Sampled values are used
by the **local** evidence scorer, not by the model. That is a better story than the one
currently told, and it is being given away.

### 4. Foreign-key inference — **fingerprints, not values**

`cygenix-infer-schema.js` scores on code evidence, containment, name similarity and
cardinality, and the stored evidence is rates and counts (`orphanRate`, containment
scores, `evidence` labels — lines 360, 423). Sampled values are read to compute the
containment test and are not retained in the result. Consistent with the brief's
preferred answer.

### 5. Errors, logs and the audit trail — **the audit is clean; the logs are not audited**

The audit entry is fully enumerable (`lib/org-store.js:130-142`):

```
seq · occurredAt · actorOid · actorEmail · effectiveRoles · action ·
resourceType · resourceId · environment · outcome · severity · detail
```

`resourceId` is `connKey(server, db)` — server and database **names**. `detail` carries
`dbAction`, `policyAction`, a refusal `reason`, `tenantId`, `approvalId` and a list of
detected destructive verbs. **No SQL text and no column values are written.** I checked
every `appendAudit` call site in `db-connect.js` and `scheduler.js`. `tenancy.js:492`
even carries a comment saying a preview is stored, never the statement.

This is checkable, unusual, and worth leading with.

**The gap is elsewhere.** Driver error messages are returned to the browser, and a failed
`CAST` message from SQL Server typically contains the offending value. There is **no
redaction rule** anywhere in the repository. Those strings also reach `console.error` in
the functions, and therefore Netlify's function logs. I found no retention policy for
those logs. **Escalate.**

### 6. Data Stream — **no customer data, because there is no customer data path yet**

The capability manifest marks `data_stream` as `preview`, with the detail *"running
against seeded demo data. No connectivity to a real database or broker yet."*
`cygenix-datastream.js` confirms it: the whole module is a pure function of a tick
number.

So there is **no retained middle and no dead-letter store holding customer rows today**.
The brief assumes there is. Describing retention, purge and tenant isolation for it would
be describing something that does not exist.

### The Globe rule generalises, with one exception

The brief's closing line for this block — *nothing finer than an aggregate reaches
storage unless a person asked for it, and where one did, it is named here* — holds for
derived data, FK evidence and the audit trail. The exception is preflight (1.2.1), and
naming it is exactly what makes the rule believable.

## 1.3 The rest

### Credentials — the weakest area, and already documented

`docs/credential-storage-audit.md` covers this in full. In summary:

- Connection strings, **including passwords**, are held in `sessionStorage` in plain
  text (`cygenix_src_conn_string`, `cygenix_conn_string`). Nothing encrypts them and
  nothing clears them on sign-out.
- Azure Function host keys in `sessionStorage`; Anthropic keys in `localStorage`, written
  from twelve files.
- Seven keys are classified **S — Secret — must not be in browser storage**, and are.
- The product claims credentials never reach Cygenix servers *and* offers scheduled jobs
  that run with no tab open. Both paths exist; both cannot be true.

**A security section cannot claim credentials are protected at rest.** It can honestly
say Entra ID authentication avoids storing a SQL credential at all, and that this is the
recommended path — that part is real (`lib/sql-entra.js`).

### Outbound TLS to customer databases — weaker than a reviewer will expect

- SQL Server: `trustServerCertificate` is taken from the connection string, and
  `db-connect.js:1169` sets it to **true whenever encryption is off**. The error handler
  at line 1346 actively advises the user to *"add trustServerCertificate=true"* — that
  is guidance to disable certificate validation.
- PostgreSQL (`buildPgConfig`, line 1292): with no `sslmode`, a recognised cloud host
  gets `{ rejectUnauthorized: false }` — **TLS without certificate validation** — and
  any other host gets `ssl = false`, **no TLS at all**. `sslmode=require` also maps to
  `rejectUnauthorized: false`, which matches libpq's own semantics but will not match a
  reviewer's expectation.

Defensible as defaults for a migration tool that must connect to legacy estates. **Not
defensible if the page says certificates are validated.**

### Application TLS and security headers — **nothing is set**

`netlify.toml` sets `Cache-Control` and nothing else. There is **no HSTS, no
`X-Content-Type-Options`, no `X-Frame-Options`/frame-ancestors, no Referrer-Policy and
no CSP.** Netlify terminates TLS and redirects to HTTPS by default, so the transport is
fine, but the headers a reviewer greps for are absent. **This is the cheapest fix in this
document and should land before the section does.**

### Encryption at rest

Azure Cosmos DB and Azure Blob Storage are encrypted at rest by the platform, always on,
and Netlify Blobs likewise. That is a platform property, not a Cygenix control, and
should be attributed as such. No customer-managed keys — `@azure/identity` is a
dependency but no Key Vault SDK is used anywhere.

### Tenancy isolation — name the mechanism, because it differs by store

- **Netlify Blobs:** a **separate store per tenant**, `projt-<tenantId>`
  (`projects.js:70`, `tenancy.projectStoreName`). Genuinely separate namespaces.
- **Azure Cosmos DB:** a **partition key per user** — `partitionKey: userId`
  (`azure-function/src/index.js`, many sites). Logical isolation within shared
  containers, enforced by the query. Jobs, schedules and saved scripts are therefore
  still per-user and not shareable within a tenant.

Two different mechanisms. Saying "logically isolated" would be true and useless; saying
"separate database" would be false.

### Authentication

Entra External ID (CIAM), MSAL browser 3.27.0, tokens verified server-side against JWKS
(`lib/entra-auth.js`, `azure-function/src/entra-auth.js`). **MSAL's cache is
`localStorage`** (`cygenix-auth-token.js:183` and four other sites), not cookies — so
there are no cookie flags to report, and the token survives the tab. Password policy, MFA
availability and session lifetime are Entra tenant configuration, **not visible in this
repository. Escalate.**

Note also that Azure-side enforcement is still off by default behind `REQUIRE_TOKEN_AUTH`
— that is documented in `CLAUDE.md` as an outstanding deployment action.

### CI

`.github/workflows/test.yml` runs the suite on push and pull request. There is **no
dependency scanning, no secret scanning, no SAST and no CodeQL** — I searched for
Dependabot, CodeQL, `npm audit`, gitleaks and trufflehog and found none. Branch
protection and review requirements are repository settings, not files. **Escalate.**

Netlify's own secrets scanner does run at build and has blocked deploys before, which is
worth a sentence because it is real and it worked.

### Hosting

| Component | Provider | Region |
|---|---|---|
| Static site, functions, blobs | Netlify | Not pinned in configuration; Netlify processes in the US |
| Function App, Cosmos DB, Blob Storage | Azure | Hostname says `uksouth`; **Cosmos and Storage not confirmed** |

Environment separation and who holds production access are not answerable from the
repository. `CLAUDE.md` already lists "is there a staging environment" as an open
question. **Escalate.**

## 1.4 For Curtis only

Unchanged from the brief, plus three the audit added:

- Model provider terms — moot for mapping, since the call is the customer's own. Still
  needed for any Cygenix-billed AI path.
- Whether a signable DPA exists; the full sub-processor list.
- Deletion on cancellation, and how it reconciles with an append-only chain.
- Breach notification commitment and timeframe.
- Which certifications are genuinely planned, and roughly when.
- **New:** what a customer must allow-list in their firewall.
- **New:** retention of Netlify function logs, which can contain driver error text.
- **New:** Entra tenant policy — password rules, MFA, session lifetime.

## 6. Names-and-types-only mapping mode

**Already true for the AI call**, which is the part that leaves the device. What sampled
values feed is the local evidence scorer (containment, orphan rate, cardinality), and
that runs in the browser against rows already fetched for the job.

So the feature the brief proposes as a differentiator largely exists. What is missing is
a **switch that stops preflight retaining example values**, and the honest description of
the split. That is a small change — a flag through `pfCheckColumn` and a line in the
preflight UI — and it would let the page say something no competitor says. Rough effort:
half a day including a test.

## What must happen before the section is written

1. **Fix the three contradictions** (Phase 2 of the brief) — the browser claim, the
   privacy policy, and the residency wording.
2. **Decide on preflight examples**: keep, add the opt-out, or stop retaining them. The
   copy differs in each case.
3. **Add the missing storage-inventory classification** for `cygenix_preflight_results`,
   and fix the scanner that missed it.
4. **Add the security headers.** Half an hour, and the section can then say they are set.
5. **Answer the escalations**, particularly the failure-report feature in 1.2.2, which
   the homepage already sells and I could not find.

Written now, the section would repeat the homepage's claim about connecting directly, or
say values never rest anywhere, or describe a Data Stream retention policy for a module
holding demo data. Any one of those is the single wrong claim the brief warns is worth
less than no section at all.
