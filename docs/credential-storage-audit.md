# Where credentials actually live

**Phase 1 of the secrets-store work. Investigation only — nothing was changed.**
Every claim below was read from the repository. Line numbers are as at the commit that
added this file.

---

## The short version

The Integrations tab tells users their connector settings are held in `localStorage`
and never on Cygenix servers. That is true, and it is the smaller half of the problem.

**Database connection strings are also held client-side, in plain text.** They are in
`sessionStorage` rather than `localStorage`, which narrows the window but does not
change the category: they are readable by any script on the page, they survive a
reload, and they are one XSS away from being exfiltrated. Alongside them sit Azure
Function host keys and Anthropic API keys, and *those* are in `localStorage`, which
survives the tab, the session and the machine's next user.

The product simultaneously claims credentials never reach our servers **and** offers
scheduled jobs that run when no tab is open. Both cannot be true. Both paths exist
today.

---

## 1. Everything written to browser storage that is credential material

`docs/storage-inventory.md` classifies all ~60 keys and is generated by
`scripts/storage-inventory.js`; `tests/storage-inventory.test.js` fails if a key is
added without a classification. Seven keys are class **S — Secret**. Here they are with
the write sites.

### Connection strings — plaintext, `sessionStorage`

| Key | Written at | Holds |
|---|---|---|
| `cygenix_src_conn_string` | `public/connect.html:716, 956, 959, 3073` | Full source connection string, including username and password when the string uses SQL auth |
| `cygenix_conn_string` | `public/connect.html:727, 1238, 1247, 3101` | Full target connection string, same |

`project-builder-app.js` reads both. Nothing encrypts them; nothing clears them on
sign-out that I could find.

`sessionStorage` is per-tab and cleared when the tab closes. That is genuinely better
than `localStorage` and worth saying in the design note — but it is still the same
trust boundary. Any script running on the page reads it synchronously, and the
console loads scripts from cdnjs.

### Azure Function host keys — `sessionStorage`

| Key | Written at | Holds |
|---|---|---|
| `cygenix_fn_key` | `public/connect.html:1237, 1277, 3100` | Host key for a user-supplied Function endpoint |

### AI provider keys — `localStorage`, and widely

`cygenix_api_key` holds the user's Anthropic key. It is written from **twelve** files:

```
public/one-to-many.html:1228, 1794      public/connect.html:841, 3194, 3526
public/insights.html:594, 986           public/data-generator.html:1232
public/object-mapping-app.js:1579, 5571 public/sql-editor-app.js:1818
public/job-editor.html:594              public/data-cleansing.html:708
public/mapper.html:782, 2135            public/dashboard-app.js:85, 9287, 9288
```

`dashboard-app.js:9287-9288` writes it to **both** `localStorage` and `sessionStorage`.
`anthropic_api_key` and `cygenix_anthropic_key` are legacy spellings of the same thing,
still written by `reports-app.js`.

These are the customer's own keys, billed to the customer — that was deliberate and is
documented in `docs/DEPLOY-remove-anthropic-key.md`. It makes the exposure *theirs*
rather than ours, which is better commercially and no better for them.

### Auth token in transit

| Key | Written at | Holds |
|---|---|---|
| `cygenix_pending_token` | `public/index.html:9` | An auth token being handed between pages |

Short-lived by design. Worth confirming it is cleared on consume rather than left.

### Connector configuration

`public/cygenix-integrations.js` keeps everything under one key, `cygenix_integrations`
(read at `:105`, written at `:109`). Its own header says so at `:13`:

> All state lives in localStorage at `cygenix_integrations`. Credentials stored
> there are browser-local — NOT a long-term secrets solution. Surface this in UI.

Of the five built connectors, two hold credential material:

- **webhook** — an optional shared secret, sent as `X-Cygenix-Signature` (`:34`, used
  at `:141` and `:156`).
- **smtp** — host, port, username and **password** (`:72`).

The other three (`json-export`, `json-import`, `csv-jobs`) are file operations and hold
nothing sensitive. Thirteen further connectors are `status: 'coming-soon'` and store
nothing because they do not exist.

## 2. The Connections page — answering the question directly

The prompt asked whether database credentials on the Connections page are also
client-side, and to say so loudly if they are.

**They are.** See §1. The full connection string — server, database, username and
password — is written to `sessionStorage` by `connect.html` on every path that
establishes or restores a connection, and read back by `project-builder-app.js`.

Two things make this less bad than it first looks, and both belong in the design note
rather than in a reassurance:

- It is `sessionStorage`, not `localStorage`. It does not outlive the tab.
- `netlify/functions/db-connect.js` takes the connection string **per request** from
  the body and does not persist it. There is no server-side copy to leak.

And one thing makes it worse: `connect.html:335` shows `db-connect` swapping
username/password for an Entra token when the string asks for it — so a
managed-identity path already exists for SQL. Where that path is used, no password
needs to be in the browser at all. It is not the default.

## 3. The SMTP path — verified

The UI says SMTP credentials are relayed to our servers at send time and then
discarded. **The code does what the UI says**, and rather carefully.
`netlify/functions/send-email.js`:

- Nothing is written to any store. The nodemailer transport is built per request and
  discarded — there is no credential cache to expire or leak. The file's own header
  states this as an enforced consequence, not an intention.
- `redact(text, secret)` (`:66`) strips the password out of anything heading for a log
  **or a response body**, specifically because SMTP servers echo the login in
  rejections (`535 5.7.8 Username and Password not accepted`).
- Requests require a verified Entra token, so it cannot be used as an open relay.
- `ALLOWED_PORTS` limits connections to 25/465/587/2525, which stops the function
  being used as a port scanner.

**This is the pattern the rest of the system should follow**, and it is worth saying so:
the SMTP path is the one place where a credential crosses to a server, is used, and is
provably not kept. Its weakness is upstream, not here — the password it receives came
out of `localStorage`.

I found no error-reporting or telemetry SDK anywhere in the repo, so there is nothing
capturing request bodies out of band.

## 4. Can a secret currently reach a log, an error or an audit entry?

| Path | Finding |
|---|---|
| SMTP | **No.** Redacted by construction in both logs and responses. |
| `db-connect` | **Probably not, but not by construction.** `:786` passes a `log` callback into the mssql retry loop; it logs driver messages, not the config. The connection string is not logged directly. There is no redactor here, so this holds by accident rather than by design — a future `console.log(config)` during debugging would leak, and nothing would fail. |
| `data-proxy` | **No.** It forwards `x-anthropic-key` verbatim without inspecting, logging or storing it, and the error logging added recently names the *action*, never the key. |
| Audit trail | **No secrets today**, but there is no shared redactor, so this is a convention rather than a guarantee. `docs/architecture-as-built.md` §4 already lists "no shared redactor with its own test suite" as a gap. |
| Telemetry / error reporting | **None exists.** No Sentry, no App Insights SDK in the client. |

Redaction helpers exist in seven files (`cygenix-privacy.js`, `send-email.js`,
`connectors.js`, and others) — **all of them local, none of them shared.** Requirement
seven of the design ("redacted by construction, not by remembering at each call site")
is therefore currently unmet everywhere except SMTP.

## 5. What server-side infrastructure is actually available

| Capability | Status |
|---|---|
| A backend we control | **Yes, two.** 11 Netlify Functions (Node) and 23 Azure Functions (Node). Both already verify Entra tokens. |
| Managed identity | **Yes, in use.** `@azure/identity` is a declared dependency of both backends, and `DefaultAzureCredential` is already used to get SQL tokens (`netlify/functions/lib/sql-entra.js`, `azure-function/src/sql-entra.js`, covered by `tests/sql-entra.test.js`). `tests/sql-entra.test.js:109` shows a `managedIdentityClientId` path, so user-assigned identity is supported too. |
| Azure Key Vault | **No SDK in use.** `@azure/keyvault-keys` appears in `package-lock.json` only transitively, via `mssql` → `@azure/identity`. No code imports it. Whether a vault is *provisioned* cannot be answered from the repo — it is an Open Question in `CLAUDE.md`. |
| A database we control | **Yes: Azure Cosmos DB**, already holding jobs, settings, connection metadata and subscriptions, partitioned on `userId`. Plus Netlify Blobs for the org store and the audit chain. |
| A place for per-tenant state | **Yes.** `netlify/functions/lib/tenancy.js` and the `cygenix-org` blob store already carry tenant identity, membership and guardrail policy. |

So the ingredients for envelope encryption exist today: an identity to authenticate
with, a document store to hold ciphertext, and a tenant boundary to scope keys to. The
only missing piece is a key-encryption key with a home.

## 6. Three things the prompt did not ask about, that matter to the design

1. **`connect.html` is where almost all of this lives.** Six of the seven secret keys
   are written from that one file. A migration has one main site to change, not
   twelve — the twelve are for `cygenix_api_key` alone, which is a separate and easier
   problem because it is the *customer's* key for a third party.

2. **Scheduled jobs already need server-side credentials.**
   `azure-function/src/scheduler-run-background.js` and `run-migration.js` run without
   a browser. Whatever they use today is the de-facto secrets path, and the design must
   account for it rather than inventing a parallel one. This is the concrete reason the
   "never on our servers" claim cannot survive the roadmap.

3. **The Entra-token path for SQL already exists and removes the need for a password
   entirely** where the target supports it (`db-connect.js:335`). For Azure SQL with
   Entra auth, the best secret is no secret. The design note should make that the
   preferred path and treat stored credentials as the fallback for SQL auth and
   on-premises SQL Server — not the other way round.
